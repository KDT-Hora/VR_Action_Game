# Research: VR小世界アクションゲーム

## R1. エンジン
- **Decision**: Unity 6
- **Rationale**: 仕様書の候補、Meta XR SDK・OpenXR対応が成熟、C#で純ロジックを分離しやすい
- **Alternatives**: Unreal(重い、C++で決定論テストの敷居が高い)、Godot(MR/シーンAPIの対応が弱い)

## R2. PCVR + 実空間スキャン(最大リスク)
- **Decision**: Meta Quest 3/3S を PC接続で使い、Meta XR SDK の MR Utility Kit(シーンモデル: 床・壁・天井・家具のラベル付きアンカー)でスキャンを取得する
- **Rationale**: ヘッドセット自身がスキャンした部屋モデルを取得でき、PCVRでの描画品質も確保できる
- **Risk**: PC接続時にシーンデータが取得できる範囲・要件(最新のSDK/ランタイム)は**Phase 0スパイクで実機確認が必要**。確認できない場合の代替:
  - (a) 固定の疑似スキャンデータで開発を進め、スキャン取得は後付け
  - (b) コントローラーで机の四隅を指定する手動スキャン(机上モードの代替)
  - (c) スタンドアロンビルドへ切替
- **Alternatives**: OpenXR汎用拡張(機種依存が強い)、ZEDなど外付けカメラ(コスト・普及度)

## R3. 決定論的生成
- **Decision**: 自前のPRNG(SplitMix64/xoshiro系)、浮動小数演算はグリッド量子化(整数セル)後に処理。空間データはセルグリッドに離散化し、生成は整数演算中心
- **Rationale**: 浮動小数点の環境差を排除し、SC-003(100回同一)を機種を問わず満たせる
- **Alternatives**: System.Random(実装差のリスク)、Unity.Random(状態がグローバル)

## R4. ステージ生成アルゴリズム(探索型)
- **Decision**: 空間データを歩行可能セルグリッドに変換→領域分割→開始地点/ゴール選定(最遠点)→BFSで到達可能性検証→敵・アイテム・ギミックをルールで配置→失敗時はシードから決定的に再試行
- **Rationale**: 単純で検証しやすく、探索型に十分。他ステージ種類は同じ基盤に配置ルールを追加するだけ
- **Alternatives**: WFC(検証が難しい)、L-system(空間制約に不向き)

## R5. 縮尺・覗き込み
- **Decision**: ステージは実寸のスキャン形状(1:1)から作り、その上に5〜20cm(既定10cm)のキャラクターを置く。プレイヤーの頭部・身体は実寸のまま。机上モードでは机の範囲、部屋モードでは床・家具の範囲がそのままステージになる(空間を縮小しない)
- **Rationale**: 覗き込みが現実の頭の動きそのままで成立する
- **Alternatives**: プレイヤー縮尺を変更(酔いやすい)

## R6. 安全
- **Decision**: プレイ範囲(境界)を空間データから算出。頭部・コントローラーが境界の閾値以内でパススルーを自動表示、ボタンで手動切替
- **Alternatives**: 常時輪郭表示(没入感を損なう)

## R7. 保存・共有
- **Decision**: JSON(バージョン付き)。共有は「生成条件+簡略化空間データ」を1ファイルにエクスポート
- **Rationale**: 他人の部屋でも同一ステージを再現するには空間データが必要

## R8. テスト
- **Decision**: Coreの EditMode テスト(決定論・到達可能性)を中心にし、PlayModeは統合スモーク
